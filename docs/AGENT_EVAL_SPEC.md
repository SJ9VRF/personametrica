# Agent evaluation specification

PersonaMetrica-Bench uses a task/trial/grader/trajectory decomposition for agent-level evaluation. The evaluator is treated as a component that can itself drift, overfit, abstain, or be gamed.

## Unit definitions

- **Task** — a requested world-state change plus explicit success, permission, tool/action, verification, and budget constraints.
- **Trial** — one attempt at a task under a named perturbation.
- **Trajectory** — observable events only: confirmations, tool calls, verification evidence, retries, and final state. Hidden chain-of-thought is neither required nor stored.
- **Grader** — a set of independently inspectable assertions over final state and/or the trajectory.

## Task coverage

The checked-in controlled suite uses three sandbox domains:

- reminders (`reminders.create`),
- notes (`notes.add`),
- tasks (`tasks.create`).

A grader must validate both the allowed **tool and action**, not just the tool name.

## Why final state is insufficient

A final state can look correct even when an agent:

- acted before required confirmation;
- skipped outcome verification;
- used a disallowed tool or action;
- produced only a partial required state;
- looped excessively;
- claimed success after an observed mismatch; or
- wrote a forged `verification.success=true` event whose observed state disagrees with the expected state.

## Graders

1. **End-state-only** — checks only resulting state.
2. **Trajectory-policy** — additionally checks permission, tool/action policy, bounded tool use, and a verification-success flag.
3. **Composite** — exposes those assertions as an explicit weighted rubric with a configurable threshold.
4. **Robust trajectory** — recomputes verification from expected/observed evidence instead of trusting self-reported success.
5. **Evidence-aware trajectory** — uses robust verification but returns `Unknown` when critical observation evidence has been redacted or is otherwise unavailable.
6. **Dense trajectory reward** — a smooth, auditable diagnostic score over state, policy, permission, verification, efficiency, and evidence integrity. It is not presented as a learned production reward model.

## Gold labels and grader calibration

Gold labels are scenario-authored from task constraints, not generated by the grader being evaluated. This remains a synthetic assertion benchmark, not independent human calibration. The release includes:

- `data/grader_disagreement_queue.jsonl` for explicit review triage;
- `annotation/trajectory_grading/` with gold/grader outputs removed from the annotator view;
- `scripts/score_trajectory_annotations.py` for agreement and Fleiss' kappa once multiple reviewers provide labels;
- `docs/GRADER_CALIBRATION_PROTOCOL.md` describing the acceptance protocol for any future human or LLM judge.

## Multi-trial protocol

The core authored suite uses **80 tasks × 10 trials = 800 trajectories**, covering all ten perturbations once per task: clean success, recoverable mismatch, unsafe shortcut, missing verification, wrong tool, wrong action, partial state, redundant loop, false success claim, and forged verification.

`reports/GRADER_RELIABILITY.md` additionally quantifies estimate variance as the number of repeated trials per task increases. Multiple trials are part of the evaluation protocol because single stochastic attempts yield materially noisier task-level estimates.

## Grader stress tests

The reliability suite applies metamorphic mutations to otherwise valid traces:

- append an irrelevant event — verdict should be invariant;
- forge a success flag — recomputed verification should be invariant;
- redact observed verification state — evidence-aware grader should abstain;
- move required confirmation after the action — grader should reject;
- duplicate tool calls beyond the budget — grader should reject.

It also sweeps the composite grader's pass threshold to expose threshold-driven false-accept changes. Checked-in results are tied to `data/grader_fingerprint.json`, so changing evaluator code requires regenerated results.

## Failure-to-data flywheel

False accepts become two artifacts:

- text correction pairs in `data/trajectory_failure_pairs.jsonl`;
- structured evidence-grounded corrections in `data/trajectory_corrections.jsonl`.

`data/trajectory_failure_splits.json` enforces task-disjoint train/dev/test partitions. `reports/TRACE_FAILURE_DATA_AUDIT.md` also reports semantic-template duplication; the current correction text is intentionally **not** used to claim semantic post-training generalization.

## Boundaries

This suite validates evaluation mechanics. It does not measure frontier-model agent capability because trajectories are controlled/synthetic. Independent human grader calibration, frontier/open-weight model trials, and real post-training remain external evidence requirements.

## Held-out evaluator attacks (v3.5)

The original ten perturbations are not treated as a complete test set for the grader itself. Five additional attack families are evaluated separately after the original evaluator design: partial verification targets, payload/state causal mismatch, unlogged actions, permission revocation, and verification that precedes the action. `CausalTrajectoryGrader` adds action presence, payload support, live-permission, full-target verification, and verification-order assertions. This is an evaluator-generalization diagnostic over authored attacks, not an adversarially generated or model-discovered attack set.
